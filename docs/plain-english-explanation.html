1. What is an AI agent?

A normal chatbot only answers questions.

An AI agent can take actions, such as:

  • Refunding a card payment
  • Increasing a credit limit
  • Replacing a card
  • Booking a flight
  • Moving money

That creates risk. A broken or manipulated agent could perform thousands of incorrect actions very quickly.

2. What does the problem statement ask us to build?

Imagine a bank has hundreds of AI agents. The bank needs a security system controlling them.

That system must answer:

  1. What is each agent allowed to do?
  2. How much money can it affect?
  3. How can one agent be stopped?
  4. How can every agent be stopped during an emergency?
  5. Can the bank later prove exactly what happened?

This security system is the “Governance Layer for Financial Agents.”

A simple analogy is an office building:

  • Employee ID card → agent identity
  • Doors they can enter → permissions
  • Company-card limit → spending limits
  • Security desk → operator dashboard
  • Deactivate badge → revoke one agent
  • Lock the whole building → fleet emergency stop
  • Security-camera history → action records

3. What Claude already designed

The existing proposal contains:

  • A central gate that approves or refuses agent actions
  • A rulebook describing what each agent may do
  • Daily spending limits
  • A button to stop one agent
  • A button to stop all agents
  • A history of decisions
  • An operator dashboard
  • A small simulated prototype

This is a solid starting point. The story is clear and the scope is realistic.

The problem is that these are almost exactly the features AmEx already requested. They show good execution, but not enough original thinking to reliably beat other teams.

4. Our upgraded idea

Our temporary product name will be MandateGuard.

Its promise is:

No AI agent can perform a financial action without receiving a one-time, tightly limited permission slip.

The important improvement is that MandateGuard will not merely answer “yes” or “no.” It will control the complete journey from request to actual execution.

AI agent → MandateGuard → One-time Action Permit → Mock bank
                    ↕
       Rules, budgets, approvals and emergency controls
                    ↕
              Operator dashboard

The mock bank will reject agents that try to contact it directly.

5. How one refund would work

Suppose a refund agent requests a $100 refund.

Step 1: Prove the agent’s identity

MandateGuard verifies that this really is the refund agent—not another program pretending to be it.

Step 2: Examine the request

It checks:

  • Is this agent allowed to issue refunds?
  • Is it allowed to access this customer?
  • Is $100 below its single-refund limit?
  • Has it already issued too many refunds today?
  • Are too many refunds happening right now?
  • Has this agent been stopped?
  • Is the whole fleet currently stopped?

Step 3: Choose one of three outcomes

  • ALLOW: safe enough to execute automatically.
  • DENY: clearly forbidden.
  • HOLD FOR APPROVAL: legitimate, but risky enough to require a person.

This third outcome is important. Banks do not want to reject every unusual but valid request.

Step 4: Reserve the money

Before approving the refund, MandateGuard temporarily reserves $100 from the agent’s available limit.

This works like a temporary card authorization.

Why?

If twenty refund requests arrive simultaneously, they must not all see the same available balance and collectively exceed the limit.

Step 5: Create an Action Permit

MandateGuard produces a digitally sealed, one-use permission containing:

  • Which agent may use it
  • Exact customer and action
  • Exact amount
  • Which rules approved it
  • When it expires
  • A unique number preventing reuse

The agent cannot change a $100 permit into a $1,000 refund.

Step 6: Execute the refund

The mock bank accepts the request only if the permit is valid.

It rejects:

  • Direct agent requests
  • Expired permits
  • Modified permits
  • Previously used permits
  • Permits issued before an emergency stop

Step 7: Record the result

If the refund succeeds, the reserved $100 becomes actual used budget.

If it definitely fails, the $100 is released.

The system then creates an Execution Receipt proving what was requested, why it was approved and what the bank actually did.

6. What “dynamic limits” means

The existing proposal only has fixed daily limits. That is not genuinely dynamic.

Our system will combine several limits:

  • Maximum amount per refund
  • Maximum amount per customer
  • Maximum amount per agent
  • Maximum amount across all agents
  • Maximum number of refunds per minute
  • Temporary limits during elevated-risk situations

Example:

An agent is allowed refunds below $1,000. A malicious agent sends fifty refunds of $900 each.

A basic system sees fifty individually valid refunds.

MandateGuard sees the rapidly growing total exposure and automatically:

  • Reduces the effective limit
  • Places new requests on hold
  • Or stops the affected agent

That is much more compelling than merely blocking one obviously oversized transaction.

7. What the audit feature really does

The current prototype links records using cryptographic fingerprints. That can reveal simple editing, but it is not completely unchangeable.

We will honestly describe it as tamper-evident, not “immutable.”

Each receipt will include:

  • Authenticated agent identity
  • Original request
  • Decision and reason
  • Exact rule version
  • Budget reservation
  • Human approval, if any
  • Actual bank result
  • Time and unique request number

We will periodically create a separately protected checkpoint. If someone later edits, deletes or rearranges records, verification will fail.

8. Our second major innovation: test rules before activating them

A bank operator might create a bad rule that accidentally blocks every refund.

Before activating a new rule, MandateGuard will replay previous requests in simulation and show something like:

This new rule would deny 37 additional requests, including 12 previously successful customer refunds.

The operator can inspect the impact before publishing the rule.

This is called “policy shadow replay,” but in plain language it means:

Test tomorrow’s rules against yesterday’s traffic before they can cause damage.

9. The prototype judges will see

We will build one area—refunds—properly rather than pretending to support every possible banking action.

The demonstration will show:

  1. A normal refund successfully changes the mock bank balance.
  2. A larger refund waits for human approval.
  3. A rogue agent attempts an unauthorized action and gets denied.
  4. The rogue agent contacts the bank directly and gets rejected.
  5. Many simultaneous refunds attempt to exceed the shared limit.
  6. MandateGuard prevents the total limit from being exceeded.
  7. Risk mode automatically tightens limits.
  8. The emergency button stops all new financial actions.
  9. An old permit is reused and rejected.
  10. An execution receipt is opened and verified.
  11. A proposed new rule is tested against historical activity.

This will be scripted and repeatable. We will not wait for random events during the presentation.

10. What each technology will do

  • React: the operator-facing website.
  • FastAPI: the main MandateGuard service.
  • OPA: checks configurable rules.
  • PostgreSQL: safely stores budgets, requests and receipts.
  • Docker Compose: starts the complete prototype with one command.
  • Mock bank: safely demonstrates real consequences without touching an actual bank.

No real customer data or banking connection is required.

11. What we will deliberately avoid

We will not initially add:

  • Machine-learning anomaly detection
  • Blockchain
  • A real bank integration
  • Complicated cloud infrastructure
  • Multiple deeply implemented banking workflows
  • An LLM inside the safety decision

The safety decision should be predictable and testable—not creative.

We may add one AI-driven agent later, but only after MandateGuard is reliable.

12. Why this can become a winning project

It will demonstrate more than a dashboard:

  • Financial understanding
  • Security thinking
  • Reliable handling of simultaneous requests
  • Clear human approvals
  • Measurable emergency response
  • Honest limitations
  • A visually understandable demonstration
  • A product that complements existing bank systems

That combination is also excellent PPI material because you can discuss product decisions, system design, security, testing and business value during interviews.
