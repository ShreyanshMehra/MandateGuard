A governance layer for financial AI agents
01 · The problem

A rulebook isn't governance if the agent can ignore it

Banks are starting to let AI agents take real financial actions. Most "AI governance" today stops at a policy document or a voluntary allow/deny API.

  • Nothing stops a misconfigured or compromised agent from calling the bank directly, bypassing the policy layer entirely.
  • Nothing stops a burst of requests from exceeding a limit under concurrent load.
  • Nothing stops an old authorization from being replayed or mutated.
  • Nothing guarantees a verifiable record of what actually happened.
02 · What we built

One action, built all the way down

MandateGuard is a real, enforced action broker for refund_payment — not an advisory service an agent can route around.

Identity

Signed agent tokens

Short-lived, verified — never self-declared.

Policy

OPA / Rego

Versioned rules return ALLOW / DENY / HOLD_FOR_APPROVAL.

Budgets

Atomic reservation

Customer, agent and fleet caps reserve together or not at all.

Permits

One-use, signed

Ed25519, 60s TTL, parameter-bound to the exact request.

Execution

Verified, not trusted

The bank signs its own result; the broker checks it.

Receipts

Every terminal action

Signed, hash-verifiable proof of what happened.

The mock bank is Docker-internal only — even an agent on the same network can't reach it. Only the broker holds the service credential.

04 · The permit lifecycle

Seven steps, no shortcuts

  1. Verify the agent's signed token.
  2. Fetch trusted customer / refundable-amount data from the bank — never from the agent.
  3. Ask OPA for a decision against the live policy.
  4. On ALLOW, reserve customer + agent + fleet budget in one locked transaction.
  5. Issue a 60-second, single-use, parameter-bound Ed25519 permit.
  6. Call the bank; verify its signed result before trusting "success."
  7. Commit or release the reservation; write a signed execution receipt.

An expired, tampered, or replayed permit is rejected — proven directly against the bank's execution endpoint, bypassing the broker, the way an attacker would.

05 · Concurrency you can't cheat

Twenty requests, ten-request cap — exactly ten, never eleven

  • Budget scopes lock in deterministic sorted order and are checked before any reservation is written.
  • Measured, not simulated — a real concurrent burst against live budget headroom lands exactly at the cap, every run.
  • Same guarantee for idempotency: ten concurrent requests sharing one key settle to exactly one action, one receipt.
06 · Governance that holds

Approval can never override a hard control

01
Fleet halt
One operator action denies every new request — commit-to-denial bound in the tens of milliseconds.
02
Agent revoke
Immediate for new requests; a monotonic epoch invalidates anything issued before it.
03
Held-action approval
Re-runs live policy and re-checks epochs before executing — a stale context is rejected, not silently approved.
07 · Audit & safe policy testing

Tamper-evident, and reversible before it's live

  • Every state change appends to a hash-chained audit log per action.
  • Signed checkpoints let an auditor detect a single edited or deleted historical event — demonstrated with a direct SQL tamper.
  • Shadow replay tests a candidate policy against real historical requests before it goes live, with a hard guarantee it can never touch a live budget, permit, or refund.

10 · Honest limitations

What this is, and isn't, yet

One action (refund_payment), one currency (USD), one local PostgreSQL instance.

Prototype dev keys and shared-secret service credentials — not hardware-backed identity or mTLS.

No guarantee of reversing a refund the bank already applied.

Tamper-evident checkpoints, not physically immutable storage.

UNKNOWN bank outcomes reconcile manually, by design — never retried blindly.

No fraud detection, no prompt-injection-prevention claim, no real LLM agent yet.

We built the deterministic safety core first. Everything above is a next step once the core is trusted — not a prerequisite for it.

11 · Close

We didn't ask the agent to behave.

We made an unauthorized, unbounded, or unverifiable financial action physically impossible — and measured it, end to end.

That's the bar a bank needs cleared before an agent touches real money.

Selected invariants

  • No bank refund without broker identity and a valid permit.
  • A permit is consumed at most once.
  • Customer, agent and fleet budgets reserve together or none reserve.
  • Approval never overrides a hard control.
  • No DB transaction stays open across an OPA or bank call.
  • Shadow replay cannot change live state.
